# Исправление проблемы массовой отправки сообщений после окончания демо периода

## Проблема

Бот отправлял **тысячи сообщений** пользователям после окончания демо периода.

### Причина проблемы

1. **`morning_sender`** и **`evening_sender`** запускаются **каждую минуту** (для точной проверки временных окон)
2. Обе функции получают все пары со статусом `past_due` и отправляют им уведомления
3. **НЕ БЫЛО проверки**, было ли уже отправлено сообщение сегодня

### Математика проблемы

Если у вас **100 пар** со статусом `past_due`:

- **Утреннее окно** (7:00-8:00 = 60 минут):
  - Каждую минуту: 100 пар × 2 пользователя = **200 сообщений**
  - За час: 200 × 60 = **12,000 сообщений**

- **Вечернее окно** (21:00-22:00 = 60 минут):
  - Каждую минуту: 100 пар × 2 пользователя = **200 сообщений**
  - За час: 200 × 60 = **12,000 сообщений**

- **Итого в день**: **24,000 сообщений** для 100 пар!

## Решение

Добавлена проверка через **Redis**, чтобы предотвратить повторную отправку сообщений в течение дня.

### Изменения в коде

#### 1. `morning_sender` (строки 67-151)

Добавлена проверка перед отправкой:
```python
# Check if notification already sent today (using Redis)
past_due_notification_key = (
    f"past_due_notification_morning:{pair.id}:{today.isoformat()}"
)
if redis_client:
    notification_already_sent = await redis_client.get(past_due_notification_key)
    if notification_already_sent:
        logger.info("Past due notification already sent today (morning), skipping")
        continue
```

После успешной отправки устанавливается флаг в Redis:
```python
# Mark notification as sent in Redis (expires at end of day)
if redis_client:
    await redis_client.setex(past_due_notification_key, 86400, "1")
```

#### 2. `evening_sender` (строки 366-451)

Аналогичная проверка для вечерних уведомлений:
```python
past_due_notification_key = (
    f"past_due_notification_evening:{pair.id}:{today.isoformat()}"
)
```

### Как это работает

1. **Перед отправкой**: Проверяется ключ в Redis `past_due_notification_{morning/evening}:{pair_id}:{date}`
2. **Если ключ существует**: Пропускаем отправку (уже отправлено сегодня)
3. **Если ключа нет**: Отправляем сообщение и устанавливаем ключ с TTL 24 часа

### Преимущества решения

- ✅ **Предотвращает спам**: Каждая пара получает максимум 2 сообщения в день (утром и вечером)
- ✅ **Использует Redis**: Быстрая проверка, не нагружает БД
- ✅ **Автоматическое истечение**: Ключи автоматически удаляются через 24 часа
- ✅ **Отказоустойчивость**: Если Redis недоступен, сообщения все равно отправляются (fallback)

## Проверка `dunning_notifications`

Функция `dunning_notifications` запускается **один раз в день** в 10:00 UTC, поэтому там проблема менее критична. Однако она также отправляет сообщения при переходе пары в статус `past_due`, что может дублироваться с утренними/вечерними уведомлениями.

**Рекомендация**: Рассмотреть добавление проверки и в `dunning_notifications`, чтобы избежать дублирования в день перехода в `past_due`.

## Результат

После исправления:
- Каждая пара со статусом `past_due` получает **максимум 2 сообщения в день** (утром и вечером)
- Вместо **24,000 сообщений** для 100 пар → **200 сообщений** (100 пар × 2 сообщения)
- **Снижение нагрузки на Telegram API в 120 раз**
